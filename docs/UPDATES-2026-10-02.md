## 2. token 抓取：为什么以前抓不到

* dsh 的 launch token **只在启动时打印一次到 stdout，不落盘**。过去只有启动器会抄它，
  于是"在终端直接 `dsh web`"时没人知道本次 token → 卡片推不出去、网关拿不到 token、
  局域网地址一打开就是"需要重新认证"。
* `connection` 服务（`dsh-client-connection`）确实持有它，但**不在服务本身上**：
  真实字段是 `HostConnectionService.browserAuth.launchToken`，服务对外只暴露
  `authenticatedUrl(baseUrl)` / `authorizeIndex()`。读 `connection.launchToken` 永远是
  `undefined` —— 抓取必然超时（本次修复前线上就是这个症状）。
* **cordis 4 的三条铁律**（都踩过）：
  1. 未注入服务的**属性访问会抛错**（`cannot get property "connection" without inject`），
     抛进启动路径会变成 unhandled rejection → dsh 直接 `fatal load failure` 起不来；
     只能 `ctx.get(name)`（拿不到返回 `undefined`）或 `ctx.inject([...], cb)`。
  2. 静态 `export const inject = ["connection"]` 是**整个插件的激活开关**：服务一旦在当前
     作用域不可见，插件永远 pending —— 卡片、注册、抓取**全部静默不执行**。
  3. 所以：**插件本体不声明静态 inject**，需要服务时在内部按需获取。

现在的抓取顺序（三条路互不依赖）：

1. `ctx.get("connection")`；
2. `ctx.inject(["connection"], scope => …)` 回调里取服务，再按
   `authenticatedUrl()` → `browserAuth.launchToken` → 兼容直读 的顺序读 token；
3. **stdout 嗅探**：dsh-web-app 会打印 `dsh web: <带 ?token= 的地址> (LAN: …)`，
   插件在模块 import 时透明包装 `process.stdout.write` 抓这一行（原样转发、原样返回）。

拿到候选后**回环自证**：`GET http://127.0.0.1:<port>/?token=…` 必须得到 `303` 才算数
（旧 token 一律 `401`）。最后写 `~/.dsh/lan/web-state.json`（含 `pid` / `source: plugin:*` /
`route` / `verified`），并往 `capture.log` 追加一行审计。

> 教训：审计函数里用了 `dirname()` 却没 `import`，异常又被自己的 `catch` 吞掉 ——
> 所谓"抓取审计"从来没落过盘，事故后完全无法从证据判断走到哪一步。

## 3. 卡片契约（用户逐字定稿）

* 外层一行（`scheduleTaskName` / `summary`）：`DeepSeek Harness本次启动地址`
* 正文首行：`# DeepSeek Harness本次token`
* 入口小节：`## 三个入口`，顺序固定 **局域网 → 阿里云 → Tailscale**
* 带 token 的只有局域网那条；阿里云与本机 tailnet 网关是**免 token 入口，只推短地址**
* `scheduleTaskId` 必须非空（否则负一屏只显示标题、正文不渲染）
* 同一轮两张卡片的 `msgId` 必须不同（否则被负一屏去重）
* 页脚写生成时间与 token 尾 6 位：用户曾因粘贴旧卡片里的旧 token 反复看到 401

## 4. 华为端点实测（2026-10-02 晚）

* 正确路径 `POST /distribution/message/cloud/claw/msg/upload`：
  * 缺 `x-trace-id` → `{"code":"0000500001","desc":"Parameter x-trace-id is empty"}`
  * `authCode` 错 → `{"code":"0000900034","desc":"The authCode is invalid"}`
  * 正常 → `{"code":"0000000000","desc":"OK"}`，响应头带 `x-nuwa-sample-state` /
    `x-nuwa-request-microservice`（说明到达了华为微服务网关）
* 路径写错 → `404 {"message":"Not Found"}`，`Server: elb`，**没有任何 `x-nuwa-*` 头**
* 当天 23:41–23:55（本地）出现约 15 分钟坏窗口：正确路径也被回成上面这种 ELB 404，
  之后 20/20、5/5、3/3 全部 200。
* 结论：**不是服务被关停**（DNS 双 A 记录正常、TLS 正常、后端参数校验照常工作），
  而是华为 ELB 层间歇性把已知路由当成未知路由；正文长度、中文编码、密钥、源 IP 均已排除。
  对策是多级投递阶梯 + 看门狗用**新进程**补推（详见 `docs/CARD-CONTRACT.md` 与主仓库文档）。
