# 端点实测记录：契约、返回码、间歇性 404 到底是谁的问题

本文只记录**在本机实测到的事实**，不记录任何真实凭据。
本文里的地址 / IP 一律是占位符或文档地址（RFC 5737 TEST-NET、`192.168.0.x`、`example.com`）。

> 适用对象：本仓库的 `hiboard_push`（`src/lib/`）与推送兜底插件 `src/push-guard/`。
> 两者走同一个上传端点，因此下面所有结论对两者同样成立。

---

## 1. 契约

| 项 | 值 |
|---|---|
| 端点 | `POST https://hiboard-claw-drcn.ai.dbankcloud.cn/distribution/message/cloud/claw/msg/upload` |
| `content-type` | `application/json; charset=utf-8` |
| 必需请求头 | `x-trace-id: task-push-<yyyyMMddHHmmss>`（格式与官方客户端一致） |
| User-Agent | `OpenClaw-TaskPusher/2.0` |
| 鉴权 | 仅请求体里的 `authCode` |
| 方法 | **只接受 POST**（对同一路径发 GET 返回 `405`） |
| 正文 | `{"data":{"authCode":"…","msgContent":[{…8 个字段…}]}}`，见 [`CARD-CONTRACT.md`](CARD-CONTRACT.md) |
| 长度 | `content` 上限 5000 字符 |
| DNS | 该域名有**两个 A 记录**，两个都实测过 |

## 2. 返回码对照（判读用）

| 观测 | 含义 |
|---|---|
| HTTP 200 + `{"code":"0000000000"}` | ✅ 成功（`"0"` 也被接受） |
| HTTP 200 + `{"code":"0000500001","desc":"Parameter x-trace-id is empty"}` | 缺 `x-trace-id` 请求头 |
| HTTP 200 + `{"code":"0000900034", …}` | **authCode 无效/未授权**（或设备侧未登录 / 动态推送开关关闭，见子码说明） |
| **HTTP 404 + `{"message":"Not Found"}`** | ⚠️ **请求没到业务服务**：响应里**没有任何 `x-nuwa-*` 头**，只有 ELB 的痕迹（`server: elb`） |
| HTTP 200 + 带 `x-nuwa-sample-state` / `x-nuwa-request-microservice` 等响应头 | ✅ 正常路径：请求**经由微服务网关**处理 |
| HTTP 405 | 用了 GET |

**判读要点**：拿"错误路径的 404"和"正确路径的 200"比响应头 ——

- 200 那次带一串 `x-nuwa-*`（微服务网关加的）；
- 404 那次**一个都没有**，只有 `server: elb`。

这说明 404 是**负载均衡层**直接给出的（后端没有可用实例 / 路由没匹配上），
请求**根本没有进入业务微服务**，所以它既不是"密钥错"也不是"参数错"——
参数错会由业务侧返回带业务码的 JSON。

## 3. 免凭据自检：怎么判断"现在是不是坏窗口"

用**故意写错的** authCode 发一次请求，看返回哪一类：

| 结果 | 结论 |
|---|---|
| `{"code":"0000900034"…}` | 服务**可达**，只是授权码不对 → 端点正常，问题在本地配置 |
| `404 {"message":"Not Found"}`（无 `x-nuwa-*`） | 处在**坏窗口**：请求没到业务服务，跟你的 authCode / 正文 / 长度**无关** |

```bash
# 注意：这是"用错误凭据探测端点可达性"，不会泄露真实授权码
curl -sS -i -X POST \
  -H 'content-type: application/json; charset=utf-8' \
  -H 'x-trace-id: task-push-20261003010000' \
  --data '{"data":{"authCode":"INVALID-FOR-PROBE","msgContent":[{"msgId":"probe_1","scheduleTaskId":"probe","scheduleTaskName":"probe","summary":"probe","result":"probe","content":"probe","source":"OpenClaw","taskFinishTime":0}]}}' \
  https://hiboard-claw-drcn.ai.dbankcloud.cn/distribution/message/cloud/claw/msg/upload
```

## 4. 实测证据：间歇性 404 是**华为侧**的坏窗口

### 4.1 现象

- 同一份字节、同一分钟：一次请求 404（`server: elb`，无 `x-nuwa-*`），下一次立刻 200；
- 2026-09-30 白天：某个进程内**连续 107 次尝试全部 404**，而把**同一份字节**
  交给新起的进程发送，**5/5、6/6 全部 200**；
- 2026-10-02 晚上：出现一段**约 15 分钟**的窗口，期间**所有**尝试方式
  （独立进程、`fetch`、`https.request`、逐个钉 A 记录）**全部 404**；
  窗口过去后，同一套测试立刻 **20/20、5/5、3/3 全部 200**；
- 坏窗口里**两个 A 记录都 404**，所以不是"某一个边缘节点挂了"这么简单。

### 4.2 排除结论

| 猜想 | 证据 | 结论 |
|---|---|---|
| **华为把这个服务关停了** | 窗口过后同样的请求立刻恢复 200，且返回头、业务码、卡片渲染完全一致 | ❌ 不成立 |
| authCode 无效 | 无效码返回的是 `0000900034`（业务码），而不是 ELB 的 404 | ❌ 不成立 |
| 正文编码 / 长度问题 | 同一份字节换个进程就 200；且 404 是 ELB 层产生的，业务侧根本没看到请求 | ❌ 不成立 |
| `msgId` 形状问题 | 换过多种 `msgId` 形状（时间戳/毫秒/uuid 前缀），窗口内外表现一致 | ❌ 不成立 |
| **华为侧 ELB 路由 / 后端实例摘除** | 404 由 ELB 直出（无任何 `x-nuwa-*`）；影响面按时段成片出现又整片恢复；与客户端实现无关 | ✅ 与证据一致 |

### 4.3 "新进程发就成功"这个经验事实

2026-09-30 的数据是：**同一个进程内**怎么发都 404（107/107），
而**换一个刚起的新进程**发同一份字节就 200（5/5、6/6）。

这是一个**经验事实，不是已解释的机制**。所以：

- 可以拿它**提高命中概率**（"失败后用新进程再发一次"是有依据的做法）；
- 但**不能**据此宣称"新进程必然成功"——2026-10-02 23:35 就出现过
  "新进程 200、同一分钟另一个新进程 404"的情况（坏窗口的影响盖过进程因素）。

> 提醒：本文**不**声称已完全理解华为侧机制。"ELB 路由/实例摘除"是与全部观测一致的
> **最简解释**，而不是从华为侧拿到的结论。可复现的是"坏窗口存在且会自己恢复"。

## 5. 工程上的应对

既然坏窗口的存在与否**不由我们决定**，就把"送达"做成概率问题、并且**必须重试**：

1. **把 404 当成可重试**，而不是永久错误。
   修前 `push-guard` 的分类是"4xx = 永久错误"→ 404 不重试 → 落在坏窗口里的推送
   **静默丢失**。现在 404 归入可重试类别（`classifyPush`），
   其余 4xx（如 405 用错方法）仍是永久错误。
2. **指数退避**：第 n 次失败后等 `基数 × 2ⁿ⁻¹`，封顶 60s。
   坏窗口的量级是几十秒到几分钟，固定间隔的少数几次尝试容易"正好全错过"，
   指数退避能让尝试**跨过**几十秒的窗口（`retryDelayMs` / `retryCount` 可配）。
3. **成功判定不能只看 HTTP 200**：必须看响应体的成功码
   （`"code":"0000000000"` 或 `"0"`）。实测存在"200 但业务码异常"的情形。
4. **失败必须留痕**：`push-guard` 把每次判定写进 `<状态目录>/push-guard/audit.jsonl`、
   把最后状态写进 `last-state.json`，因此"哪一轮没推出去、是不是 404"可以直接查文件。
5. 如果需要在**更长的窗口**（十几分钟）里兜底，可把 `retryCount` 调大
   （配合封顶 60s 的退避），或在宿主侧加"稍后用新进程补推"的外部兜底。

### 一个刻意的取舍：宁可少重试，也不要制造重复卡片

重试分类里，"2xx 但响应体没有 `code` 字段"**视为成功**，不重试 ——
否则会在卡片**其实已推成功**的情况下再推一遍，凭空多一张重复卡片。
同理，404 之所以可以放心重试，是因为它**在业务侧根本没被处理**（ELB 直出）。

## 6. 与手机侧有关、但容易被误判成端点故障的两件事

- **设备离线 / 未登录华为账号**：返回 `0200100004` 系列子码；
- **负一屏动态推送开关关闭**：同样返回 `0200100004`（不同子码）——
  此时"推送成功但手机不显示"，第一反应往往是"端点坏了"。

排查顺序：**先看返回码，再看手机负一屏**（我的 → 设置/动态管理）。
