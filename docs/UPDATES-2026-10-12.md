# 更新 2026-10-12：兼容 dsh 0.2 的 peer 范围（不修会被新版的准入检查直接拒载）

本次只有一件事，但是**升级 dsh 0.2 的硬前提**：放宽 `peerDependencies` 上界，
否则新版 dsh 会在启动时把整个 bundle 拒掉，`hiboard_push` / `hiboard_verify` 直接消失。

---

## 1. 背景：dsh 0.2 新增了插件兼容性准入检查

dsh 0.2 起，**profile 启动和插件安装都会检查**每个插件声明的
`peerDependencies`（只针对 `@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*`）
是否匹配当前运行时版本。不匹配的插件会被拒绝加载；
**bundle 不匹配则整个 bundle 被跳过**，并记入 `skippedBundles`。

原始实现（`dsh-app-boot/lib/index.js`，0.2.0-rc.2，`evaluatePluginCompatibility()`）关键两行：

```js
if (name !== "@deepseek-ai/dsh" && !name.startsWith("@deepseek-ai/dsh-")) continue;

if (requirement.trim() === "" ||
    !semver.satisfies(runtimeVersion, requirement, { includePrerelease: true })) peers[name] = range;
```

两个容易踩的点：

1. **只筛 `@deepseek-ai/dsh*`** —— `@deepseek-ai/cordis`、
   `@deepseek-ai/schemastery` 会被 `continue` 跳过，**不参与**准入判定。
   所以它们保持 `<5.0.0-0` / `<4.0.0-0` 完全没问题，不要误改。
2. **`{ includePrerelease: true }`** —— 用普通 `semver.satisfies()`（不带该选项）自行验算，
   会把结果**大面积误判为不兼容**。验算时必须带上这个选项，否则结论不可信。

## 2. 症状

在 dsh `0.2.0-rc.2` 上，本插件的旧声明：

```json
"@deepseek-ai/dsh-tools":    ">=0.0.1-rc.1 <0.1.0 || >=0.1.0-rc.1 <0.2.0-0",
"@deepseek-ai/dsh-settings": ">=0.0.1-rc.1 <0.1.0 || >=0.1.0-rc.1 <0.2.0-0"
```

`<0.2.0-0` 把 `0.2.0-rc.2` 排除在外 → 判定不兼容：

```
dsh-hiboard-push DENIED -> {
  "@deepseek-ai/dsh-tools":    ">=0.0.1-rc.1 <0.1.0 || >=0.1.0-rc.1 <0.2.0-0",
  "@deepseek-ai/dsh-settings": ">=0.0.1-rc.1 <0.1.0 || >=0.1.0-rc.1 <0.2.0-0"
}
```

后果：bundle 被跳过 → **`hiboard_push` 与 `hiboard_verify` 两个工具都不会注册**，
按错误提示的方式推送会失败；严重时启动直接非零退出。

## 3. 修法

把两条 DSH peer 的上界从 `<0.2.0-0` 放宽到 `<0.3.0-0`：

```json
"@deepseek-ai/dsh-tools":    ">=0.0.1-rc.1 <0.1.0 || >=0.1.0-rc.1 <0.3.0-0",
"@deepseek-ai/dsh-settings": ">=0.0.1-rc.1 <0.1.0 || >=0.1.0-rc.1 <0.3.0-0"
```

同步改动两处（**根 `package.json` 与 `src/package.json` 都要改**，
否则以根目录安装时仍会被拒）：

| 文件 | 改动 |
|---|---|
| `src/package.json` | 两条 peer 上界 → `<0.3.0-0`；版本 `0.1.1` → `0.2.0` |
| `package.json` | `dsh-tools` peer 上界 → `<0.3.0-0`；版本 `0.4.0` → `0.5.0`；描述补「兼容 dsh 0.2」 |

> 根 `package.json` 原本**没有**声明 `@deepseek-ai/dsh-settings`，
> 本次也**没有**添加 —— 该插件已不再使用设置面板（见 `NOTICE` 第 1 条），
> 声明一个用不到的 peer 只会凭空多一个不兼容风险点。

### 版本号为什么这样跳

- `src/package.json`（即发布用的 `dsh-hiboard-push`）：`0.1.1 → 0.2.0`。
  新增了对 dsh 0.2 的支持，属于**功能新增**，按语义化版本走 minor。
- 根 `package.json`（仓库自身）：`0.4.0 → 0.5.0`，同理。

## 4. ⚠️ 关键：改了源码不等于生效（pnpm 注入副本）

dsh profile 的 `node_modules/<pkg>` 不是符号链接，而是 pnpm **注入（复制）** 的副本。
`<profile>/node_modules/.modules.yaml` 的 `injectedDeps` 会写明它来自哪个目录：

```yaml
injectedDeps:
  "E:/dsh-vendor/dsh-hiboard-push-main":
    - "node_modules/dsh-hiboard-push"
```

因此**只改源目录的 `package.json` 不会生效** —— 准入检查读的是副本。
改完必须重新注入：

```bash
dsh plugin --profile web install
```

然后确认副本真的更新了：

```powershell
Select-String -Path "$env:USERPROFILE\.dsh\profiles\web\node_modules\dsh-hiboard-push\package.json" `
              -Pattern "dsh-tools"
# 期望看到 <0.3.0-0，而不是 <0.2.0-0
```

> 历史教训：2026-10-12 曾以为改了 `node_modules` 里的文件就完事，
> 结果后来的 `pnpm install` 用 vendor 副本把改动**静默覆盖**回去了。

## 5. 验证

### 5.1 用 dsh 0.2 的真实准入函数验算（推荐）

不要自己重写判定逻辑，直接调用 0.2 的 `evaluatePluginCompatibility()`：

```js
import { evaluatePluginCompatibility } from "@deepseek-ai/dsh-app-boot";
evaluatePluginCompatibility(require("./package.json"), {}, "0.2.0-rc.2");
// undefined = 通过；有返回值 = 被拒，返回值里的 peers 就是不合格的那几条
```

本次实测结果（运行时 `0.2.0-rc.2`）：

| 插件 | 结果 |
|---|---|
| `dsh-hiboard-push`（修复后） | **ACCEPTED** |
| `dsh-push-guard` | ACCEPTED |
| `dsh-token-broadcast` | ACCEPTED |
| `dsh-entry-startup` | ACCEPTED |
| `dshmarket` | ACCEPTED |

对照组（换回修复前的声明）→ `DENIED`，且拒绝项精确等于上面那两条 peer ——
说明这个检查确实会拦，不是空跑。

### 5.2 干跑（不启动 dsh）

```bash
dsh web --dump-config 2>&1 | Select-String "skip|denied|incompatible"
# 期望：无输出
```

## 6. 另一条可选路径：精确版本豁免

dsh 0.2 也提供官方豁免，写在 profile 自己的 `compatibility.json`：

```bash
dsh plugin --profile web version-exemptions
dsh plugin --profile web allow-version dsh-hiboard-push@0.2.0 --dsh-version 0.2.0-rc.2 --accept-risk
```

**但不推荐**：豁免是"精确 包@版本 → 精确 dsh 版本"的绑定，
**插件升级或 dsh 再升级都不会继承**，每次都要重新授权。
放宽 peer 范围是一次到位、且对未来 0.2.x 都有效。
